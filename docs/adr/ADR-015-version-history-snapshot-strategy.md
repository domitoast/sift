# ADR-015: 版本歷史採完整快照，編輯後寫入，保留最近 20 版

## 狀態

已接受（Day 11）

## 背景

Day 10 加上編輯功能之後，舊的內容就永久消失了。
`document_version` 表在 Day 4 就建好，但一直沒有寫入邏輯。

實作前有四個問題沒有答案，每一個都有多種合理做法。

---

## 決定 1：存「舊的」還是存「新的」

### 考慮過的選項

追蹤同一份文件從 A 編輯成 B、再編輯成 C 的過程：

| | 建立時 | 編輯時 | 歷史內容 | 主表 |
|---|---|---|---|---|
| **甲（採用）** | 存初版 | 存**新的** | A, B, C | C |
| 乙 | 不存 | 存**舊的** | A, B | C |
| 丙 | 存初版 | 存舊的但跳過第一次 | A, B | C |

**使用者最初選的是「乙的編輯策略 + 甲的建立策略」，
但那個組合會產生重複——建立時存了 A，第一次編輯前又存一次 A。**

這個衝突是在追蹤實際資料時才發現的，不是在討論時。

### 決定與理由

採用甲。

**一、歷史必須包含「現在這一版」。**
乙的做法下，使用者打開版本列表會看到 A 和 B，但文件現在是 C——
最新的那一版不在列表裡，看起來像少了一個。

**二、不需要特例判斷。**
丙要在程式裡寫「如果這是第一次編輯就不要存」。
那種條件三個月後沒有人看得懂為什麼存在。

### 代價

`document.content` 會與最新那一版的內容重複一份。

**可接受**：兩張表互不影響——讀文件只碰 `document`，讀歷史只碰 `document_version`。
多存一份現在的內容，換到「歷史是完整的」。

## 決定 2：完整快照，還是只存差異

### 考慮過的選項

| | 第 3 版存什麼 | 讀第 3 版 | 空間 | 實作 |
|---|---|---|---|---|
| **完整快照（採用）** | 整篇內容 | 一次查詢 | 大 | 簡單 |
| 只存差異 | 「B 改成 C 的地方」 | 讀第 1 版 + 套用 2 次差異 | 小很多 | 要寫差異演算法與套用邏輯 |

### 決定與理由

採用完整快照。**依據是實際計算，不是偏好。**

| 情境 | 一版大小 | 20 版 | 100 篇文件 |
|---|---|---|---|
| 一般文字筆記 | 2–5 KB | 100 KB | **10 MB** |
| 很長的技術文章 | 50 KB | 1 MB | 100 MB |

**10 MB。而且 PostgreSQL 對大的 TEXT 欄位會自動壓縮（TOAST），實際佔用更少。**

存差異能省下的空間，以這個規模來說不值得換那個複雜度。

> **這與 ADR-011 是同一個判斷方法，但結論相反。**
> 那次算完發現一萬使用者會產生 2 GB，所以改了設計。
> 這次算完發現只有 10 MB，所以不改。
> **方法一致，結論由數字決定。**

### 重新評估的時機

若日後支援檔案上傳或很大的文件（單版超過 1 MB），重新計算。

## 決定 3：保留最近 20 版

### 考慮過的選項

- 不限制：一篇改過 500 次的文件會留下 500 份完整快照
- 保留最近 N 版（採用，N = 20）
- 保留最近 N 天

### 決定與理由

**20 是估的**，依據是「一般人回頭找版本很少翻超過十幾個」。

選「版本數」而非「天數」的理由：天數會讓「很久沒改的文件」失去全部歷史，
而那正是最可能需要回溯的情況。

**修剪的算術值得記錄，因為它很容易差一：**

```
剛存完第 21 版
  oldestToKeep = 21 - 20 + 1 = 2
  刪掉 version_number <= 1
  剩下第 2–21 版 = 20 筆
```

**這段邏輯是專案裡唯一會主動刪除資料的地方，因此有專門的測試，
且該測試除了斷言「剩 20 筆」，還斷言「第 1 版真的查不到」——
只測前者的話，減法差一也會通過。**

## 決定 4：列表不含內文

`GET /documents/{id}/versions` 回傳 `versionNumber`、`title`、`createdAt`，
不含 `content`。要看內容打 `/versions/{number}`。

理由與 ADR 未編號的文件列表相同：20 個版本每個都帶內文，
一次列表就是好幾百 KB 的回應，而畫面上根本用不到。

實作用 interface projection（`DocumentVersionSummary`），
因此 SQL 本身就不會 SELECT `content`。

**列表沒有分頁**——上限固定 20，是「答得出最多幾筆」的清單。

> **「回傳清單就要分頁」這條規則的真正內容是：
> 答不出上限的才要分頁。**

## 附帶決定：權限檢查在 document 層做

`document_version` 沒有 `user_id`。擁有者由 `document_id` 指向的那篇文件決定。

因此兩支版本 API 都是兩步驟：

```
① requireOwnedDocument(userId, documentId)   ← 查不到就 404
② 才查它的版本
```

### 考慮過的替代方案

在 `document_version` 也放一份 `user_id`（反正規化），
這樣權限就能寫進查詢條件，與 ADR-013 一致。

**否決理由**：多一份需要維護同步的資料。
文件的擁有者若日後可以轉移，兩張表就得一起改，而漏改一邊不會有任何錯誤。

**代價**：這是本專案唯一「權限不在查詢條件裡」的地方（違反 ADR-013 的原則），
因此把檢查抽成 `requireOwnedDocument()` 一個方法，
讓「漏做」在 code review 時看得出來。

---

## 後果

### 好處

- 編輯不再讓舊內容永久消失
- 歷史是完整的，包含現在這一版
- 空間有上限，不會無限成長

### 代價

- `document.content` 與最新版本重複
- 超過 20 版的舊歷史會被刪除，且不可復原
- 版本 API 的權限檢查是兩步驟，比其他 endpoint 多一次查詢
