# ADR-011: refresh token rotation 採「原地更新」而非「每次新增一列」

## 狀態

已接受（Day 8）。**補充 ADR-010**，不取代它。

## 背景

ADR-010 決定 refresh token 儲存於資料庫以支援撤銷。
Day 8 進一步決定實作 **token rotation**（每次換發時作廢舊的、發新的），
以取得 **重複使用偵測（reuse detection）** 的能力。

實作前計算資料量時發現問題。

### 觸發這份 ADR 的計算

若 rotation 實作為「每次 INSERT 一列新的」：

| 使用情境 | 每人每天新增 |
|---|---|
| 一天使用 2 小時 | 9 列 |
| **前端持續運作（整天掛著）** | **96 列** |

以最壞情況、保留 7 天計算：

| 使用者數 | 穩定保有列數 | 空間 |
|---|---|---|
| 1,000 | 67 萬 | 200 MB |
| 10,000 | 672 萬 | **2 GB** |

而**不做 rotation** 時，一個 session 只需 1 列——10,000 人約 20 MB。

**差距 100 倍。**

## 考慮過的選項

### 選項 A：不做 rotation

refresh token 七天內固定不變。

- 優點：一個 session 一列，資料量最小
- 缺點：**盜用完全無法偵測**。小偷與使用者共用同一張票七天，
  伺服器只看到「同一張票被用了很多次」，那是完全正常的現象

### 選項 B：rotation，每次 INSERT 新列（原方案）

- 優點：實作最直觀，舊紀錄完整保留可供稽核
- 優點：可往回追溯任意代數
- 缺點：**資料量 100 倍**
- 缺點：需要更積極的清除排程才能控制成長

### 選項 C：rotation，原地更新同一列（採用）

新增欄位 `previous_token_hash`，換發時：

```
previous_token_hash ← 目前的 token_hash
token_hash          ← 新產生的值
```

- 優點：**一個 session 永遠只有一列**，資料量與選項 A 相同
- 優點：rotation 與盜用偵測都有效
- 缺點：**只能往回追溯一代**
- 缺點：需要一份 V3 migration

## 決定

採用選項 C。

## 理由

**「只能追溯一代」在偵測上不構成損失。**

盜用偵測的判斷條件是「一張已被使用過的票又被拿來用」。
在 rotation 之下，這件事**必然在小偷動手後的下一次換發就會發生**——
不需要往回追更多代。

追溯多代的價值只在**事後稽核**（重建完整的 token 鏈）。
本專案沒有稽核需求，屬於 YAGNI。

**100 倍的空間差距，換取一個用不到的能力，不划算。**

## 附帶決定：rotation 不延長 expires_at

換發時 `expires_at` 保持原值，不往後推。

**理由**：七天是「這個 session 的絕對上限」，不是「閒置多久才過期」。
若每次換發都延長，只要持續使用就永遠不必重新登入，
等於這個 session 沒有生命週期上限。

**代價**：使用者每七天一定要重新輸入一次密碼，即使他天天在用。
本專案認為這個代價可以接受。

## 偵測邏輯

```
收到 refresh token X
   ↓
hash(X) 與 token_hash 相符？ → 正常換發
   ↓ 否
hash(X) 與 previous_token_hash 相符？
   ↓ 是
   ⚠️ 這張票已經被換掉了，卻又有人拿它來用
   → 判定為盜用
   → 作廢該使用者「所有」的 refresh token
   ↓ 否
   查無此票 → 單純的無效 token，回 401
```

## 後果

### 好處

- 資料量與不做 rotation 相同
- 保有盜用偵測能力

### 代價

- 無法重建完整 token 鏈（無稽核能力）
- 需維護 `previous_token_hash` 欄位的正確性
- **誤判風險**：前端逾時重試可能觸發假警報。
  正式系統會加上數秒的寬限期，本專案暫不實作

### 重新評估的時機

- 若日後有法規稽核需求，需保留完整 token 歷史 → 改回選項 B
- 若誤判造成實際困擾 → 加入寬限期機制

## 附註

本決定由使用者在實作前提出資料量疑慮而促成，
是「擔心效能之前先算數字」原則的第三次實際應用
（前兩次：`fetch_job` 資料量、refresh token 儲存成本）。
