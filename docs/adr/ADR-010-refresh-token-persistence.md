# ADR-010: refresh token 儲存於資料庫以支援撤銷

## 狀態

已接受（Day 6）

## 背景

JWT 一經簽發即無法撤銷——伺服器不保存任何紀錄，
因此沒有任何機制能讓一個尚未過期的 token 失效。

但 `docs/API_DESIGN.md` 中已承諾：

```
POST /auth/logout    使 refresh token 失效    204
```

這兩件事互相矛盾。且 V1 migration 中沒有任何資料表儲存 token，
代表該承諾在當時的設計下無法兌現。

此矛盾於 Day 6 實作認證時才被發現，屬 Day 3 API 設計階段的疏漏。

## 考慮過的選項

### 選項 A：refresh token 也做成純 JWT，不儲存

- 優點：實作最簡單，簽發時多一個 `type: refresh` 欄位即可
- 優點：完全無狀態，不需查詢資料庫
- 缺點：**`POST /auth/logout` 無法兌現承諾**。
  使用者按下登出後，refresh token 仍有效七天
- 缺點：token 若外洩，在過期前完全無法補救

### 選項 B：refresh token 儲存於資料庫（採用）

新增 `refresh_token` 表，記錄擁有者、雜湊值、過期時間、撤銷時間。

- 優點：登出真正有效
- 優點：可實作「登出所有裝置」
- 優點：可偵測 token 盜用——同一個 refresh token 被使用兩次，
  代表其中一方是攻擊者（正常流程下 refresh token 用過即換新）
- 缺點：每次 refresh 需查詢一次資料庫
- 缺點：需要清除機制，否則過期紀錄會持續累積

## 決定

採用選項 B。

## 理由

**API 設計已經承諾了登出功能。** 選 A 等於回頭刪除需求，
而登出是使用者對任何有帳號的系統的基本期待。

關於「查詢資料庫」的成本：refresh 只在 access token 過期時發生，
以 15 分鐘的 TTL 計算，單一使用者一天約 60 次。
相較於每個 API 請求都要驗證的 access token（維持無狀態），
這個頻率完全可以接受。

**這個設計實際上是混合式的**：
- access token 無狀態（快、不查資料庫）
- refresh token 有狀態（慢、但可撤銷）

兩者的取捨剛好互補：高頻的那個要快，需要控制的那個要可撤銷。

## 資料量評估

「儲存 token 會不會造成資料量過大」是實作前提出的疑慮，實際計算：

| 情境 | 一年筆數 | 空間 |
|---|---|---|
| 單人使用（每週登入 1–2 次） | 約 80 筆 | 約 12 KB |
| 一萬使用者、每人每天登入一次 | 365 萬筆 | 約 550 MB |

`refresh_token` 將是本專案最小的資料表之一——
比 `fetch_job` 更小，遠小於帶有全文的 `fetched_item`。

疑慮不成立。**這個判斷來自「擔心效能之前先算數字」的原則。**

## 安全設計

**資料庫儲存的是 token 的 SHA-256 雜湊值，不是 token 本身。**

理由與密碼相同：資料庫外洩時，攻擊者拿到雜湊值無法反推出可用的 token。

此處使用 SHA-256 而非 BCrypt——refresh token 是 256 bits 的隨機值，
暴力破解本來就不可行，不需要刻意放慢。
BCrypt 只會讓每次 refresh 多等 100 毫秒。

**判斷原則：雜湊演算法的選擇取決於「被保護的值有多容易猜」。**
人類記得住的密碼用慢的，密碼學隨機值用快的。

## 後果

### 好處

- 登出、撤銷、登出所有裝置皆可實作
- 具備偵測 token 盜用的基礎

### 代價

- 每次 refresh 多一次資料庫查詢
- 需要排程清除過期紀錄（尚未實作）

### 待辦

- [ ] 過期 refresh token 的清除排程
- [ ] token 重複使用的偵測與自動撤銷（進階，可能不做）

### 重新評估的時機

若日後拆分為多個微服務，且各服務都需要驗證 refresh token，
集中式的資料庫查詢可能成為瓶頸，屆時可考慮改用 Redis。
