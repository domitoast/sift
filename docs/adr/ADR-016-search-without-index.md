# ADR-016: 搜尋暫不建索引，維持單純的 LIKE 查詢

## 狀態

已接受（Day 12）

## 背景

文件數量增加後需要搜尋功能。實作了 `GET /api/v1/documents?q=關鍵字`，
以 `LIKE '%關鍵字%'` 比對標題。

**實作後實際量測**：灌入 5 萬筆測試資料，執行查詢計畫分析。

```
EXPLAIN ANALYZE
SELECT id, title FROM document
WHERE user_id = 1 AND deleted_at IS NULL
  AND LOWER(title) LIKE LOWER('%doc-49999%');
```

結果：

```
Index Scan using idx_document_user_list on document
  Index Cond: ((user_id = 1) AND (deleted_at IS NULL))
  Filter: (lower((title)::text) ~~ '%doc-49999%'::text)
  Rows Removed by Filter: 50030
Execution Time: 10.926 ms
```

**判讀**：既有索引只處理了「哪些是我的」，
`LIKE` 的部分是把該使用者的 50,031 筆全部取出後逐筆比對，丟掉 50,030 筆。

**為什麼索引幫不上**：`LIKE '%關鍵字%'` 開頭是萬用字元。
B-tree 索引是排序過的結構，能快速找「以某字串開頭」，
但「包含某字串」的目標可能散佈在任何位置，無從縮小範圍。

## 考慮過的選項

### 選項 A：維持現狀，不建索引（採用）

- 優點：零成本
- 優點：程式碼最單純，沒有額外的擴充相依
- 缺點：耗時與該使用者的文件數呈線性成長

### 選項 B：`pg_trgm` + GIN 索引

把字串切成三字一組建索引，使 `LIKE '%x%'` 也能走索引。

- 優點：**對中文可用**——它機械地切三個字，不需要知道怎麼斷詞
- 優點：一份 migration 即可，`pg_trgm` 是 PostgreSQL 內建的 contrib 模組，
  不需要自訂 Docker image
- 缺點：索引本身佔空間，且寫入時要維護
- 缺點：為了一個目前不存在的問題付成本

### 選項 C：`tsvector` 全文檢索 + 中文斷詞擴充

- 優點：最正統，支援詞彙權重、相關度排序
- 缺點：**PostgreSQL 內建的斷詞設定不支援中文**——
  中文沒有空格，`simple` 設定會把整句當成一個詞
- 缺點：需要 zhparser 或 pg_jieba 擴充，得自建 Docker image（約半天）
- 缺點：解決的是「相關度排序」的問題，而本專案只需要「找得到」

## 決定

採用選項 A。

## 理由

**依據是實際的數字，不是偏好。**

| 使用者的文件數 | 預估耗時 |
|---|---|
| 5 萬（實測） | 11 ms |
| 50 萬 | 約 110 ms |
| 500 萬 | 約 1.1 秒 |

**本專案是個人知識庫。合理的上限是數千篇——在那個規模下耗時不到 1 毫秒。**

> **這是「擔心效能之前先算數字」的第三次應用，也是第二次得到「不要優化」的結論。**
>
> - ADR-011（refresh token）：算完發現一萬使用者一年 2 GB → **改設計**
> - ADR-015（版本歷史）：算完發現 100 篇文件 10 MB → **不改**
> - 本案：算完發現實際規模下小於 1 ms → **不改**

**選項 C 特別值得記錄為什麼否決**：它解決的是「哪一筆比較相關」，
而本專案的需求只是「找得到」。**功能更強不等於更適合。**

## 後果

### 好處

- 沒有額外的相依與維護成本
- 程式碼可讀性最高

### 代價

- 只搜標題，不搜內文（內文掃描成本更高）
- 「記得內容但忘記標題」時找不到
- 沒有相關度排序，結果依建立時間排列

### 重新評估的時機

**明確的觸發條件**：

- 單一使用者的文件數超過 **5 萬**，或
- 搜尋的 p95 延遲超過 **200 ms**

達到任一條件時，第一步是加 `pg_trgm` + GIN 索引（選項 B），
而不是直接跳到全文檢索。
