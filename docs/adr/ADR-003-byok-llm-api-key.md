# ADR-003: LLM 呼叫採 BYOK（使用者自帶 API key）

## 狀態

已接受（Day 2）

## 背景

系統需要呼叫 LLM API 為每篇 FetchedItem 產生摘要。

SRS 初稿的 FR-3.9 寫的是「LLM 呼叫應受每日配額限制」，
隱含假設是**系統持有一份共用額度**，再分配給使用者。

開發者提出質疑：實際使用時是用自己的 Claude 額度，
系統沒有理由預設要提供額度給使用者。

## 考慮過的選項

### 選項 A：系統持有共用 API key

- 優點：使用者不用設定，開箱即用
- 缺點：成本由系統擁有者承擔；多使用者時會互相搶配額；
  key 一旦外洩影響所有人

### 選項 B：BYOK — 使用者自帶 API key（採用）

每個 User 在設定頁填入自己的 LLM API key，摘要時用該 User 的 key 呼叫。

- 優點：成本歸屬正確（誰用誰付）；沒有共用配額競爭；
  符合實際使用情境
- 缺點：使用者需要自行申請 key；系統必須安全地保管敏感資料

### 選項 C：混合（系統提供試用額度，用完後需自帶 key）

- 優點：體驗最好
- 缺點：兩套邏輯都要實作，21 天內不值得

## 決定

採用選項 B（BYOK）。

## 理由

成本歸屬是正確的架構原則。Cursor、Notion AI 等工具皆提供 BYOK 選項。
對本專案而言，開發者本身即是使用者，BYOK 是唯一誠實的設計。

## 後果

### 對需求的影響

- 新增 FR：User 可設定 / 更新 / 刪除自己的 LLM API key
- 修改 FR-3.9：配額的角色從「限制使用者」改為「防止爆量」
  （例如每日最多 200 次呼叫，避免排程設錯而狂打 API）
- 若 User 未設定 key，FetchedItem 停留在 `NEW` 狀態，不視為失敗

### 對資料模型的影響

- `user` 表新增 `llm_api_key_encrypted` 欄位
- 需要一組加密金鑰（存於環境變數，不進版控）

### 對安全設計的影響（重要）

- API key **不得明文儲存**，須加密後入庫
- API key **不得回傳前端**，只能回傳遮罩形式（例如 `sk-...c123`）
- API key **不得出現在任何日誌中**
- 這三條會加入 NFR 與 Code Review 檢查表

### 代價

- 多一組加解密邏輯要實作與測試
- 使用者首次使用需要額外設定步驟

### 重新評估的時機

若未來要開放給不懂技術的使用者，可考慮加上選項 C 的試用額度。
