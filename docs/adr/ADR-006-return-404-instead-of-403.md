# ADR-006: 對無權限資源回傳 404 而非 403

## 狀態

已接受（Day 3）

## 背景

使用者 A 對使用者 B 的資源發出請求，例如 `GET /api/v1/documents/42`，
而該文件屬於 B。系統該回傳什麼狀態碼？

HTTP 規範中，403 Forbidden 的語意為「已認證，但無權存取此資源」，
在語意上是最精確的選擇。

## 考慮過的選項

### 選項 A：403 Forbidden

- 優點：語意精確，符合 HTTP 規範原意
- 優點：除錯時可立即分辨「資源不存在」與「無權限」
- 缺點：**洩漏資源是否存在**。攻擊者可對 `/documents/1` 至 `/documents/9999`
  逐一發出請求，依回應碼區分哪些 id 存在，
  藉此推知系統資料量、id 分布，甚至判斷特定資源是否曾被建立

### 選項 B：404 Not Found（採用）

對不屬於自己的資源，一律回應「不存在」。

- 優點：不洩漏任何資源存在與否的資訊
- 優點：與業界主流做法一致（GitHub 對無權限的私有 repo 即回傳 404）
- 缺點：開發者除錯時無法從回應碼分辨真實原因

## 決定

採用選項 B。所有資源查詢在權限檢查失敗時一律回傳 404。

## 理由

本專案的 `document`、`source` 皆為使用者私有資源。
「某使用者擁有 id 為 42 的文件」這項事實本身即屬隱私。

安全設計上的通則是：**在語意精確與資訊最小揭露之間，優先選擇後者。**

## 後果

### 好處

- 消除透過列舉 id 探測資源的攻擊面
- 前端處理邏輯簡化：所有「拿不到」的情況都是 404

### 代價

- 開發與除錯時，無法從回應碼分辨「資源不存在」與「無權限」
- **緩解措施（必做）**：伺服器端日誌必須明確記錄實際原因，
  例如 `access denied: user=5 attempted document=42 owned by user=9`。
  回傳給客戶端的一律是 404，但日誌中必須留下真相

### 實作注意

權限檢查必須發生在 Service 層而非 Controller 層，
且查詢時應直接以 `WHERE id = ? AND user_id = ?` 過濾，
而非先查出資料再比對擁有者——後者容易在某些路徑上遺漏檢查。

### 重新評估的時機

若日後開放團隊共享功能，資源不再全屬私有，
可針對「已知存在但無權限」的情境改回 403。
