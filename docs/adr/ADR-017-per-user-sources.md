# ADR-017: 訂閱來源歸屬於個別使用者，不做共用來源池

## 狀態

已接受（Day 13）

## 背景

實作訂閱來源時，使用者提出改為「系統提供一份確認可用的來源清單，
使用者只能從中選擇訂閱」。

**提出的動機**（原話）：

> 每個來源的抓取方法都不一樣，如果有人提出一個完全不一樣的網址、
> 甚至怎麼爬都爬不了那更麻煩，不如我先確認那些網站是確定可以爬取的再說。

這個動機是合理的，但它建立在一個前提上，而那個前提需要先釐清。

## 前提的釐清：RSS 是標準格式

「每個網站的爬法都不一樣」對**爬 HTML** 是正確的，但本專案讀的是 RSS / Atom。

RSS 存在的目的就是消除這個問題——它是標準的 XML 結構，
一個解析器可以處理絕大多數的 feed。

**至於「使用者只知道首頁網址」**：HTML 的 `<head>` 有一個慣例標記
（RSS autodiscovery）：

```html
<link rel="alternate" type="application/rss+xml" href="/feed.xml">
```

因此可以從首頁自動找出 feed 網址。

**反過來說**：限制來源清單其實無法解決使用者的顧慮——
當使用者想訂閱的東西不在清單裡（例如某個 GitHub repo 的 releases），
他一樣訂不了，除非管理員每次手動加。

## 考慮過的選項

### 選項 A：來源歸屬於個別使用者（採用，即現行設計）

```
source (id, user_id, name, url, type, enabled)
```

- 優點：與 Document、Source 的既有模式一致，權限檢查一樣寫進查詢條件
- 優點：使用者可以訂閱任何有 feed 的網站
- 缺點：兩個使用者訂閱同一個網址會產生兩筆 source，抓取兩次

### 選項 B：共用來源池 + 訂閱關係

```
source       (id, name, url, type)               ← 全域
user_source  (user_id, source_id, enabled)       ← 新表
fetched_item (id, source_id, summary, ...)       ← 全域
user_item    (user_id, fetched_item_id, status)  ← 新表
```

- 優點：**100 個使用者訂同一個來源，只抓一次**
- 優點：學習價值較高（多對多關聯、全域狀態與每人狀態的拆分）
- 缺點：需要兩張新表、一份 migration，且今日產出的一半需重寫（約 4 小時）
- 缺點：**需要角色系統**才能決定「誰有權往公共池新增來源」，而本專案沒有
- 缺點：每個查詢多一層 join

## 決定

採用選項 A。

## 理由

### 一、選項 B 與 ADR-003（BYOK）衝突

B 的主要好處是「省下重複成本」。但實際計算：

| 100 人訂同一來源 | 成本 | A | B |
|---|---|---|---|
| 抓 RSS | 幾十 KB，**免費** | 100 次 | 1 次 |
| LLM 摘要 | 一篇約 $0.001–0.01 | 100 次 | ？ |

摘要若共用，就必須回答「用誰的 API key」。
ADR-003 決定 BYOK——每個使用者自己付。因此只有兩條路：

- 摘要仍各自進行 → **B 只省下免費的那一半**
- 系統統一付費 → **ADR-003 作廢**

**B 省下的是免費的部分，省不掉花錢的部分。**

### 二、好處在本專案的規模下為零

省重複抓取只在「很多人訂同一個來源」時有意義。本專案目前只有一個使用者。

### 三、原始顧慮有更便宜的解法

「使用者填了抓不動的網址」不需要靠限制清單解決，
只需要**在建立來源時先試抓一次**：

```
使用者送出網址
   ↓
① 直接當 feed 解析 → 成功就用
   ↓ 失敗
② 當 HTML 解析，尋找 <link rel="alternate"> → 找到就用
   ↓ 找不到
③ 回 400：「這個網址沒有提供 RSS」
```

**不能用的來源根本進不了資料庫，而且完全不需要改資料模型。**

排在 Day 15（抓取實作）一併完成。

## 後果

### 好處

- 資料模型與既有的 Document / Source 模式一致
- 權限檢查維持「寫進查詢條件」（ADR-013），無例外
- 使用者可訂閱任何提供 feed 的網站

### 代價

- **重複抓取**：若日後使用者數量成長，同一個熱門來源會被抓多次。
  對來源網站不友善，可能被限流或封鎖
- 放棄了多對多關聯的實作經驗

### 重新評估的時機

**明確的觸發條件**：

- 使用者數超過 **50**，且出現「同一個 URL 被 10 個以上使用者訂閱」的情形
- 或收到來源網站的限流 / 封鎖

屆時的第一步不必立刻改成選項 B，可先做**抓取層的去重**：
排程執行時把相同 URL 的來源合併成一次 HTTP 請求，結果分發給各個 source。
那個做法不需要改資料模型。
