# ADR-002: 抓取內容與知識庫文件採 staging → curated 兩層設計

## 狀態

已接受（Day 2）

## 背景

系統中存在兩種內容：

1. **從外部來源抓回的文章** — 別人寫的，有原始網址與發布時間，原文不應被編輯
2. **使用者自己寫的筆記** — 可編輯、需要版本歷史

需要決定它們在資料模型上如何切分。這個決定會主導整個 ER 設計。

## 考慮過的選項

### 選項 A：兩張表完全分開（Article / Document）

- 優點：語意清晰，各自的欄位不會互相污染
- 缺點：搜尋、標籤、附件等功能要實作兩套；「把文章轉存成筆記」需要跨表複製

### 選項 B：一張表，用 `origin` 欄位區分

- 優點：搜尋 / 標籤 / 附件只需一套程式碼；轉存只是改欄位
- 缺點一：欄位稀疏——`source_url`、`published_at` 對手寫筆記永遠是 null
- 缺點二（關鍵）：**管線的髒資料會混進知識庫**。抓回來的內容可能重複、摘要失敗、等待 retry。
  這些半成品與使用者精心撰寫的筆記同表，導致每次查詢知識庫都必須記得加上狀態過濾條件，
  漏加的那一次就是 bug

### 選項 C：staging → curated 兩層（採用）

```
Source → FetchJob → FetchedItem（staging）--promote--> Document（curated）
                                                          ▲
                                          使用者手寫 ──────┘
```

- `FetchedItem`：管線的工作區。承載 dedup 的 unique constraint、retry 次數、失敗原因、狀態機
- `Document`：知識庫的成品。用 `origin`（MANUAL / FETCHED）區分來源，維持單一表的查詢便利

## 決定

採用選項 C。

## 理由

**兩者的生命週期本質不同**：

| | FetchedItem | Document |
|---|---|---|
| 寫入模式 | 高頻批次寫入 | 低頻使用者編輯 |
| 失敗處理 | 需要 retry、DLQ | 不適用 |
| 併發控制 | dedup 的 unique constraint | optimistic lock |
| 資料品質 | 可能是垃圾、重複、半成品 | 一律是成品 |

把生命週期不同的東西放進同一張表，會讓兩邊的規則互相干擾。

同時，選項 C **保留了選項 B 的主要優點**——知識庫仍是單一表，
搜尋、標籤、附件只需一套實作。

## 後果

### 好處

- 深度戰場（pipeline）與外殼（知識庫）在資料層即被隔離，改任一邊不影響另一邊
- 查詢知識庫時不需要記得過濾狀態，因為裡面本來就只有成品
- dedup 與 retry 的複雜度被關在 staging 層

### 代價

- 多一張表、多一個 promote 步驟
- 需要決定 FetchedItem 的保留策略（promote 之後是否刪除、保留多久）

### 待決

- FetchedItem 的資料保留期限（暫定：promote 後保留 30 天供追查，之後清除）

### 重新評估的時機

若 FetchedItem 與 Document 的欄位重疊度超過八成、且 promote 邏輯變得無足輕重，
可考慮合併回單表。
