# ADR-009: 輸入正規化置於 DTO 邊界而非 Service

## 狀態

已接受（Day 5）

## 背景

註冊 API 需要對 email 做正規化（去除前後空白、轉小寫），
理由是使用者常會輸入 `"  Kevin@Example.COM  "`，
若原樣儲存，之後以 `kevin@example.com` 登入將查無此人，
且資料庫的唯一約束無法阻止「同一信箱的不同大小寫寫法」重複註冊。

初版實作將正規化寫在 `UserService.register()` 中。

**此設計由整合測試
`register_shouldNormalizeEmailBeforePersisting` 發現缺陷**：
輸入 `"  MixedCase@Example.COM  "` 回傳 400 而非 201。

原因是執行順序：

```
Jackson 反序列化 → @Valid 觸發驗證 → 進入 Controller → 呼叫 Service
                        ↑                                    ↑
                   在這裡被 @Email 擋下              正規化寫在這裡，從未執行
```

`@Email` 看到前後空白即判定格式不合法，請求根本沒到達 Service。

**實際影響**：使用者複製貼上 email 時多帶一個空白（極常見），
收到的錯誤訊息是「email 格式不正確」，
而他盯著畫面上看起來完全正確的 email，無從得知問題所在。

## 考慮過的選項

### 選項 A：修改測試，改用不含空白的輸入

- 優點：零改動
- 缺點：**掩蓋缺陷而非修正**。真實使用者仍會遇到這個問題

### 選項 B：放寬 `@Email` 或改用自訂驗證器

- 優點：正規化仍留在 Service
- 缺點：自己寫 email 格式驗證極易出錯；
  且問題根源是「順序」而非「規則太嚴」

### 選項 C：在 DTO 的 compact constructor 正規化（採用）

Java record 的 compact constructor 在物件建立時執行，
**早於驗證註解**，因此驗證看到的是已清理的資料。

- 優點：順序正確；資料一進入系統邊界即被清理
- 優點：之後每一層都能假設 email 已正規化
- 缺點：正規化邏輯出現在 DTO，有人會認為那屬於 Service 的職責

## 決定

採用選項 C。同時**保留** `UserService` 中的正規化作為第二道防線。

## 理由

**原則：資料一進入系統邊界就清理乾淨，之後每一層都能假設它是乾淨的。**

關於「正規化算不算業務邏輯」的爭議：
去空白與轉小寫屬於**輸入清理**，不是業務規則——
它不涉及任何領域知識，只是消除同一份資料的不同書寫形式。
放在輸入邊界是合理的。

保留 Service 中的重複處理，理由有二：

1. Service 是 public 方法，可能被 Controller 以外的程式碼呼叫
   （例如日後的批次匯入功能），不保證都經過該 DTO
2. 單元測試直接建構 `RegisterRequest` 呼叫 Service，
   這條防線讓 Service 本身的正確性不依賴上游

對已正規化的字串再執行一次是**冪等操作**，無副作用。

## 後果

### 好處

- 帶有空白或大寫的 email 能正確註冊
- 驗證註解看到的永遠是乾淨資料
- 與既有的 defence in depth 思路一致
  （程式檢查 + 資料庫約束、DTO + Service 雙重正規化）

### 代價

- 正規化邏輯出現在兩處，修改時需同步
- 緩解：兩處皆有註解交叉指向本 ADR

### 這次事件本身的價值

**手動測試通過三次，缺陷仍存在**——因為手動測試時
使用的都是「乾淨」的輸入。是自動化測試強迫寫出
「使用者可能輸入什麼」的情境，才暴露了問題。

這是 Day 5 最重要的一課：
**測試的價值不是證明程式正確，而是找出你沒想到的情況。**

### 重新評估的時機

若日後正規化規則變複雜（例如需處理 Gmail 的 `+tag` 或 `.` 忽略規則），
應抽出獨立的 `EmailNormalizer` 類別，由 DTO 與 Service 共同呼叫。
