# ADR-014: 以 optimistic lock 處理編輯衝突，版本號由呼叫端攜帶

## 狀態

已接受（Day 10）

## 背景

Day 10 加上編輯功能後，立即出現 **lost update（更新遺失）**。

實測情境（真的跑過，不是推論）：

```
1. A 讀取文件，內容是「1. 預算」
2. B 讀取同一份文件，內容也是「1. 預算」
3. B 儲存 →「1. 預算 / 2. 時程」
4. A 儲存 →「1. 預算 / 3. 人力」
5. 結果：B 寫的「2. 時程」消失，且伺服器回 200，B 永遠不會知道
```

**不需要「同時」。兩人相隔五分鐘也一樣。**

原因是 UPDATE 的 WHERE 只檢查主鍵：

```sql
UPDATE document SET title=?, content=? WHERE id=63
```

`id` 永遠是 63，所以這句 UPDATE 永遠成功。

## 考慮過的選項

### 選項 A：不處理（last write wins）

- 優點：零成本
- 缺點：**會安靜地弄丟資料**。使用者收到 200，以為存好了
- 缺點：單人使用時看不出問題，多裝置或多人協作時才爆

### 選項 B：pessimistic lock（悲觀鎖）

讀取時就對資料列加鎖（`SELECT ... FOR UPDATE`），其他人必須等待。

- 優點：衝突不可能發生，不需要處理衝突後的復原
- 缺點：**鎖必須跨越「使用者思考的時間」**。A 打開文件編輯十分鐘，
  這段期間 B 完全動不了——而 HTTP 是無狀態的，
  伺服器根本不知道 A 什麼時候會送出，甚至不知道他是不是關掉分頁走了
- 缺點：容易產生 deadlock 與連線耗盡
- **適用場景**：衝突「很常發生」且交易「很短」，例如扣庫存

### 選項 C：optimistic lock，版本號由呼叫端攜帶（採用）

讀取時回傳 `version`，編輯時呼叫端把它送回來，伺服器比對。

- 優點：**沒有任何鎖**，不佔用資源，不會 deadlock
- 優點：適合「讀多寫少、衝突罕見」——本專案正是如此
- 缺點：衝突發生時使用者的編輯會被拒絕，要自己重做
- 缺點：API 多一個必填欄位，呼叫端要負責帶回來

### 選項 D：optimistic lock，但用 HTTP 的 ETag / If-Match

同樣的機制，但版本號放在 HTTP 標頭而非 request body。

- 優點：更符合 HTTP 語意，是 REST 的標準做法
- 缺點：呼叫端要處理標頭，測試與除錯時較不直觀
- 缺點：本專案的使用者仍在學習階段，放在 body 裡「看得見」比較有價值

## 決定

採用選項 C。

**並且採用兩層防護，因為它們防的是兩種不同的情況：**

| 層 | 防什麼 | 實作 |
|---|---|---|
| ① Service 明確比對版本 | **「五分鐘前讀的」** | `if (!document.getVersion().equals(request.version()))` |
| ② `@Version` | **「同一毫秒的兩個請求」** | Hibernate 自動加 `AND version=?` |

## 理由

**為什麼不用 pessimistic lock**：它要求鎖存活於「使用者思考的期間」。
在 HTTP 這種無狀態、且使用者隨時可能關掉分頁的環境下，
那個鎖不知道什麼時候該放開。

**為什麼一層不夠**：`@Version` 單獨使用時擋不住本專案實測到的情境——
每個 HTTP 請求都重新載入文件，載到的一定是最新版本，
過期的版本號在呼叫端手上，不在伺服器載入的物件裡。

反過來，只做明確比對也不夠：兩個請求可能都通過比對（都讀到 version=3），
然後一前一後寫入。那個毫秒級的空隙要靠 `@Version` 補。

**這與註冊的兩道防線是同一個模式**（ADR 未編號，見 `UserService.register`）：
程式檢查負責「給人看得懂的錯誤訊息」，底層機制負責「保證正確」。

## 附帶決定：`version` 為必填

`UpdateDocumentRequest.version` 標記 `@NotNull`。

**若允許省略，呼叫端只要不送這個欄位就能繞過衝突偵測——那等於沒做。**

## 附帶發現：回應必須在 flush 之後組裝

實作後首次驗證發現：編輯成功的回應帶著**更新前**的 `version` 與 `updatedAt`。

原因是 Hibernate 預設把 UPDATE 累積到交易提交時才送出，
而 `version`（由 Hibernate 遞增）與 `updatedAt`（由資料庫 trigger 更新）
都是「UPDATE 執行後才確定」的值。

**後果**：使用者儲存成功後拿到舊的 version，
他馬上再改一次就會收到 409——而那個「別人」是他自己。

**修正**：在組裝回應前呼叫 `documentRepository.flush()`。

**原則：回應若包含由資料庫產生的值，必須先 flush 才讀得到。**

## 後果

### 好處

- 資料不會被安靜地覆蓋
- 衝突時呼叫端收到 409 與目前的版本號，可據此重新載入
- 不使用任何鎖，無 deadlock 風險

### 代價

- API 多一個必填欄位，前端必須正確地帶回來
- 衝突時使用者的編輯內容會遺失（伺服器不保留），需要他自己重做
- **沒有做「自動合併」**——真正的協作編輯需要 CRDT 或 OT，
  那是完全不同量級的工程，明確在 out-of-scope

### 重新評估的時機

- 若衝突頻繁到使用者抱怨 → 考慮欄位層級的合併，或改用即時協作機制
- 若日後開放 API 給第三方 → 改用 ETag / If-Match 較符合 HTTP 標準
